# Bundled data files

## `disposable_email_blocklist.conf`

Domains that hand out throwaway mailboxes. Loaded by
`speedpycom/services/email_domains.py`.

**Source:** <https://github.com/disposable-email-domains/disposable-email-domains>
**File:** `disposable_email_blocklist.conf` on `main`
**Licence:** CC0-1.0 (public domain dedication) — no attribution required, but
recorded here so the next person knows where to get a fresh copy.

### Refreshing it

There is no automation on purpose: a signup gate that silently changes what it
rejects, on a schedule, is not something to leave unattended.

```bash
curl -sS -o speedpycom/data/disposable_email_blocklist.conf \
  https://raw.githubusercontent.com/disposable-email-domains/disposable-email-domains/main/disposable_email_blocklist.conf
```

Then, before committing, check the diff has not swallowed a real provider:

```bash
for d in gmail.com googlemail.com outlook.com hotmail.com yahoo.com icloud.com \
         me.com protonmail.com proton.me fastmail.com aol.com gmx.com zoho.com \
         yandex.com qq.com web.de; do
  grep -qxF "$d" speedpycom/data/disposable_email_blocklist.conf \
    && echo "FALSE POSITIVE: $d"
done
```

That check is the point of doing this by hand. One bad entry in an upstream pull
request and you stop accepting signups from a major provider, and the only
symptom is a quiet drop in conversions. `speedpycom/tests/test_email_domains.py`
runs the same assertion, so a bad refresh fails the suite.

**Do not edit this file to add your own domains.** It is replaced wholesale on
every refresh, so your edits would vanish. Put project-specific domains in
`blocked_email_domains.txt` instead — see AGENTS.md.

Why this list and not a bigger one: it is ~8,000 vetted domains rather than the
100,000+ aggregated lists, which carry many more false positives. Blocking a
real customer costs more than letting a throwaway signup through.
